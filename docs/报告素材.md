## 4. 关键实现点（可写进“如何把 UML 转成代码”）

1. **先建数据模型**：把类图中的实体落成 `db.py` 的表；`inventory` 主键为 `(room_type_id, date)`，
   `orders.order_no`、`idempotency.key`、`rooms(hotel_id, room_no)` 等唯一约束与设计一致。
2. **状态机独立**：`domain.py` 维护订单与房间的允许转换；服务层只调用 `_check_transition`，
   避免状态判断散落在各处。
3. **库存条件更新**：`repository.deduct` 用一条带条件的 UPDATE 完成“检查 + 扣减”，
   并发时只有一个事务能成功；`booking.create_order` 在 `with conn` 中逐晚扣减，任一晚失败整体回滚。
4. **价格快照**：下单时把每晚价格写入 `order_nights`；改单时未变动的日期沿用旧价，
   新增日期用当前生效价，订单总价由账单重算。
5. **账单与收款分离**：`bills` 汇总房费/早餐/在店消费/取消应扣，`payments` 逐笔记录，
   `paid` 与 `unpaid` 始终满足“已收 + 未收 = 应收”。
6. **审计与隐私**：写操作统一调用 `AuditService.record`；查看手机号全号调用
   `record_privacy_view` 生成 `VIEW_FULL_PHONE` 日志；列表/老板视角默认脱敏。

## 8. 与实验二设计的差异（报告需说明）

- 数据库由 MySQL 改为 SQLite，便于单机原型运行；表结构与唯一约束按实验二设计实现。
- 界面按实验二设计实现为 Tkinter 桌面端（`--gui`），同时保留 CLI；未实现 Web 端与逐像素视觉还原。
- 一个订单只支持一个房型，多房型订单未实现；这是当前原型的主要简化。
- 调价审批实现了“超过 5 倍需审批、7 天未批自动失效”，但未做酒店端审批进度页面。
- 未实现真实支付、短信/推送、图片上传；资质照片在原型中只保留字段。
